# Security — DSH++ LAN access

## What is enforced

- Every forwarded HTTP request and WebSocket upgrade requires a valid independent gateway session before any upstream request. Unknown paths, static assets, uploads and SSE are included, even when native DSH has no authentication on them.
- Only the gateway's GET/HEAD /lan and /lan/ form and POST /lan/login are public. An existing native cookie/launch URL, Authorization header or forged forwarding header is not gateway authentication.
- Strict configured public Host/full Origin/Fetch-Metadata validation occurs before any loopback Host/Origin rewriting. Mutating methods/login/logout and WebSocket require same-origin Origin. No CORS credential access or arbitrary forward-proxy destinations.
- Upstream must be a fixed numeric loopback HTTP origin. Startup completes the native public launch exchange and cookie-authenticated HTML check before binding publicly. Redirects are not followed. Native 401/403 remain failures. No native credentials are synthesized and no signing store or Connection method is modified.
- Gateway and native credentials are separate. Native launch URL/cookie are never returned to the browser. Incoming cookies are not forwarded; upstream Set-Cookie cannot issue/overwrite gateway sessions. The browser gets a cryptographically random opaque 256-bit cookie; only a SHA-256 lookup key is retained. Cookie attributes: HttpOnly, SameSite=Strict, Path=/; HTTPS adds Secure and __Host- prefix.
- Sessions are memory-only, bounded (default 1024), and expire absolutely (default 8h, programmable maximum 24h). Expiry/logout/re-login close owned in-flight HTTP/SSE/WebSocket; stop aborts partial login reads/outbound connections and closes listeners/sockets. Restart revokes all gateway sessions. Session-cookie theft still grants access until revocation/expiry.
- Token comparison uses fixed-size SHA-256 hashes and timingSafeEqual; tokens require 32–256 UTF-8 bytes, no outer whitespace/control characters. Generate high-entropy values. Login attempts reserve budgets before asynchronous work: 5 attempts per real TCP peer per 5 minutes, bounded to 1024 peers. X-Forwarded-For never identifies a peer. Successful attempts also consume budget.
- Login bodies are capped at 1024 bytes with a 10s deadline and exact token field validation. HTTP header/request deadlines and rejection socket closure bound incomplete requests; Node rejects ambiguous parser framing. Proxy strips hop-by-hop/Connection-nominated fields, reframes payloads explicitly, does not buffer/decompress content, and respects pipe backpressure.
- Gateway responses use no-store; login uses no scripts/storage/external resources, restrictive CSP, same-origin referrer policy, nosniff and frame denial. Errors never echo credentials, native launch URLs, provider errors or certificate contents.

## Deployment assumptions and limits

**DSH must explicitly bind only to loopback** and have no alternate LAN-reachable listener, port forward, old proxy or other direct path. The host plugin checks the public webServer.host is 127.0.0.1 before enabling. This verifies that native carrier configuration, not every other process/network mapping; the operator must verify no alternate entry exists. Native Settings/ConfigEditor owns configuration persistence; the plugin does not directly rewrite profiles, rebind native sockets or change firewalls.

The gateway protects unauthenticated remote entry, not all possible DSH vulnerabilities. Logged-in users have full agent authority; there is no per-user/read-only/RBAC isolation. Same-origin script execution, compromised browsers, native code execution, local processes that can reach loopback/read process state, stolen gateway cookies/tokens and network-level denial of service remain outside this boundary. Page data already delivered cannot be recalled after logout. Host-only cookies are not port-isolated by browsers; do not host mutually untrusted services on the same hostname, and prefer TLS.

HTTP transmits token/cookie/content without encryption and exposes them to active/passive network attackers. Use direct trusted HTTPS or a controlled encrypted network. TLS certificate provisioning/renewal is external. A proxy-terminated TLS/forwarded-header trust mode is deliberately not supported. Some official GUI features require a secure context.

The settings plugin stores DSH_PLUSPLUS_LAN_TOKEN through native credentials. Only explicit local Generate returns the newly committed value; no existing-secret read API is added. Slow credential writes stay serialized through actual commit (no timeout that pretends rollback), and subsequent metadata failure does not discard the one-time generated value. Non-sensitive enabled/origin/port/TLS paths persist through native Settings/ConfigEditor with revision checks. Settings management POSTs are serialized, bounded to 8 KiB/5s body input and require local native authentication/full same-origin checks. /api/dsh-plusplus is blocked at the gateway before HTTP or upgrade forwarding, and a fixed internal marker also rejects proxied manager requests. **This protects the custom management interface, not administrator permissions:** an authenticated LAN operator can still change native settings/credentials through standard APIs or agent tools. Do not use this as a local-only administration/RBAC guarantee.

The plugin obtains authenticatedUrl through public native Connection and sends token/launch URL/TLS bytes over an inherited IPC channel to its owned child, with no inherited environment or secret argv/output. Unload, disable, rotation and parent disconnect stop the child; a 2s parent fallback uses SIGKILL. Native cookie expiry bounds gateway sessions. Before expiry the plugin automatically re-establishes the gateway from the current native launch URL, revoking existing sessions. Native 401/403 remain failures. Unexpected child failure is shown as error until settings are applied again, with no unauthenticated fallback. TLS inputs reject nonregular/empty/over-256-KiB files and use nonblocking bounded reads.

The plugin does not modify installed DSH files, native authentication, browser globals, session history, or user files. Configuration writes are limited to native Settings/ConfigEditor and credentials APIs.

## Verification and reports

Run npm run check and optional DSH_VERIFY_ROOT=/absolute/path/to/dsh npm run verify:host. Tests must prove zero anonymous hits on deliberately unprotected upstream endpoints and upgrades, not merely native API 401. Reports should include package/Node/DSH versions and a redacted reproduction. Never include token values, native launch URLs, cookies, private keys or private session content in public issues.
